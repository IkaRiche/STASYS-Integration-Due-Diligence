# STASYS — Evidence access and IP boundary
**External evaluation governance · v0.1**

## Executive proposition

A technically serious integrator can obtain **testable external claims, genuine live output, independently checked hardware observations and comparative metrics** without acquiring the original source code or underlying mathematical operators.

**Public information is not a substitute for proof.** The evaluation must be designed so that the integrator can select an admissible challenge, observe the actual qualified native implementation and verify externally measurable consequences. These actions are compatible with internal IP protection but do not guarantee zero reverse-engineering risk.

## Public vs controlled vs restricted

| Disclosure level | May be shared | Excluded |
|:--|:--|:--|
| **PUBLIC** | High-level mathematical objective, functional interfaces, test identifiers, scoped measurement figures, read-only sanitized diagrams and externally observable results | Implementation algorithms, detailed state representation, source, firmware, raw private logs, unreviewed patent material |
| **CONTROLLED EVALUATION** | Owner-operated genuine native process and hardware demonstration, bounded reviewer-chosen negative controls, verifiable signed result extracts, full claim ceilings | Unrestricted binaries, user-selectable secret internal parameters, unlimited query oracle |
| **RESTRICTED AGREEMENT** | Narrow technical audit only if separately approved by IP/legal counsel | No default right to distribute, adapt, derive or sublicense technology |

A confidentiality agreement alone does not prevent all reverse engineering or behavioral approximation. Prefer to keep executable and hardware artifacts in owner custody until the rights, applicable rules and economic terms justify further access.

## How to verify without seeing source

1. Fix a publicly reviewable **claim**, tested function, limits and comparison.
2. Identify source-owned test evidence and bind it to an opaque, owner-attested build identifier.
3. Allow the partner to choose admissible test variants unknown to the presenter in advance (where the existing implementation supports them).
4. Collect an independent view of the input and output, not just the candidate's own success message.
5. Run controls, including failure cases, and show all outcomes with original denominators.
6. Re-run the same case where permitted and compare externally observable behavior; separate internal causality audit from behavioral reproducibility.
7. State which parts were performed on **real hardware**, which in a **digital physical model**, and which remain **future evaluation proposals**.

## What the partner may rightfully request

- Description of *required input categories* with types, units, source quality, cadence and provenance;
- What outputs mean, including refusal and error semantics, and who can authorize physical action;
- Actual measurements on pinned builds and physical platforms;
- How a reported benefit was independently observed and compared to a conventional reference;
- Replay trace completeness and evidence custody, with an agreed causal explanation ceiling.

None of those questions requires revealing internal computational topology or the construction of the LMA operators.

## Important legal status

This repository has **no source-code license**. All underlying proprietary IP, including LMA research and related patentable mechanisms, remains under owner control. A contract concerning evaluation, data custody, reverse engineering, firmware access or technology licensing requires separate written authorization and legal review. Any patent/publication strategy should be assessed before expanding disclosure.
